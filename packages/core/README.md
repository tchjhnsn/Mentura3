# Reflect core

The headless core of Reflect, in plain TypeScript with no database and no Next.js. The web app imports it as `@reflect/core/<module>`. The plan for it is `docs/design/HEADLESS_REFLECT_2026-11-10.md`: one core, with a git repository or our Postgres as the host of a person's records.

## Where things are

| Path | Holds |
|---|---|
| `src/site-page.ts` | A site page's Markdown (plan "Appearance, Virtu and the site editor", PRs 3 and 4): the component library (`COMPONENTS`, grouped Media, Writing, You, From your tiles, Household, Shared domains), and the one strict parser and serializer of its MDX subset: a component sits on its own line as a self-closing tag with literal values only (`<Photo src="https://..." alt="..." />`, `<PostList limit={3} />`, `<Part source="adventures/<id>" view="card" />`). Expressions, spreads, imports, exports, children and tags outside the library are refused with the line they are on (`parsePage`, `checkPage`); addresses must be https, http or a site path. The site editor and the public renderer both use it. Also Home's and Writing's templates (`homeTemplate`: the profile card, the person's line, the latest posts, links), page paths (`isPagePath`), part sources (`parseSource`: `adventures/`, `ventures/`, `household/`) and the access rule for parts on a public page (`mayShowPart`: the owner shared it, and a household part also has the household creator's OK). Since PR 5 a visual component (`VISUAL_COMPONENTS`: Photo, Gallery, Quote, Callout, Profile card, Part) also takes `shape` and `frame` as literal values, names from the site's Virtu catalog (`BLOCK_SHAPES`, `BLOCK_FRAMES`, held to `packages/virtu/site/looks.loaded.json` by `web/src/server/site-design.test.ts`); any other name, or either value on another component, is refused with the reason. |
| `src/site-mdx.ts` | A site page as MDX for the exported project (PR 5): `escapeMdxProse` escapes `{`, `}` and `<` in prose outside inline and fenced code, so MDX reads them as characters; `pageToMdx` writes the components as tags and each `<Part>` as `<Part snapshot="<id>">` when its source is in the allowed parts (`snapshotId` names the snapshot by its content), dropping any other part and any line the parser refuses; `looksUsed` lists the shapes and frames a page names. |
| `src/site-export-pages.ts` | The pages in the exported Next.js project (PR 5), called by `site-export.ts`: `content/pages/<path>.mdx` (Home is `index.mdx`), `content/parts/<id>.json`, `app/design.css` (the site's Virtu CSS with the blocks' shapes and frames, mapped onto the page's colours), `lib/pages.ts`, and `components/reflect/*.tsx`, a component map drawing what Reflect's renderer draws with the same class names, rendered by next-mdx-remote (pinned, `MDX_REMOTE`) with `blockJS` off, since the values are literals. |
| `src/interest-catalogue.ts` | The real things Get to know you shows (`interest-items.json`, built by `scripts/interest-items.mjs`): 36 books (Open Library covers) and 36 podcast shows (Apple Podcasts artwork; `--only <area>` rebuilds one area). Music was taken out 2026-11-19, each with tags and the people behind it. The areas the dashboard card offers, `related` (same maker, then shared tags) and `becauseOf` for the "Because you picked" row. |
| `src/interests.ts` | The levels of making, doing and knowing (Torian, 2026-11-19), one record per interest whatever door wrote it. Three modes: Make, Do, Know. Commitment, shared by all three (after Stebbins): Curious, Tried it, Now and then, Toward a goal (a goal with an end, met or not), Regular practice, Way of life. Depth of knowing, for a subject and for each of its fine details (after Bloom, with appreciation): Heard of it, Follows it, Appreciates it, Understands it, Studies it, Explains it, Teaches it; the top two are earned before people. Skill, for Do and Make (Dave's psychomotor levels): Copy, Steady, Precise, Adapts, Second nature. Do adds a role (participant, competitor, coach, organiser), Make whom it is for (self, gifts, commissions, a living), Know the ways of coming to know it; every fact says whether the person told us, it was imported, or Reflect noticed it: the source kinds stated, import and noticed of `src/value-source.ts`, with the older ids told and imported read by `interestSource`. `sentence` reads a mode in plain words; `fromCraft` reads a Scholē craft through the model. Not built: earning rungs from what the person finishes, badges. Stored as the work app's hidden kind `interest` (web `interests-store.ts`, actions `pick_interest`, `set_interest`, `set_interest_area`). |
| `src/craft-interests.ts` | A kept Scholē craft read as a Make interest (one record per real interest, Torian, 2026-11-19). `craftAsInterest` takes a craft record (the work kind `craft`) and its acts and returns an `Interest` with ref `craft:<id>`, source stated, and Make's levels from `fromCraft`: drawn is Curious, trying is Tried it, practising is Regular practice; the Dreyfus stage gives skill (Novice Copy, Advanced beginner Steady, Competent Precise, Proficient Adapts, Expert Second nature). What only a craft has rides along as `craft`: its group, state, stage, what drew the person, how it was learned, how many friends vouch, tries, what was made (acts newest first, and the record's made text), its first project's name and its page (`/life/work/crafts/<id>`). It reads; it writes nothing. Not built: writing crafts as interest records. |
| `src/structure.ts`, `src/onboarding.json` | The onboarding questions and the stances a hold can take, as typed values. |
| `src/person.ts`, `src/onboarding.ts` | The person's stores as pure functions over `PersonState` (facts, relationships, holds and attributes, each with its dates and the source of its value), and the onboarding reducer Me still uses. `readPersonState` reads a stored record, older shapes included: a missing source is stated and the old `fromJournal` source is journal. |
| `src/value-source.ts` | Where a field's value came from (Torian, 2026-11-20: journal entries, AI conversations and other places are sources of field values, not life nouns). `SOURCE_KINDS` is the closed set, read with W3C PROV's wasDerivedFrom in mind: `stated` (the person typed it), `journal` (entry id and quote), `conversation` (conversation id and quote), `import` (connector or file name and item id) and `noticed` (the ids of the person's records Reflect noticed it in). Every kind but stated starts proposed until the person confirms it (`startStatus`, `confirmSource`; `lean/Reflect/Sources.lean` proves it). `readValueSource` and `sourceKindOf` read older values: missing and told are stated, imported is import, fromJournal is journal. `SOURCE_JSON_SCHEMA` is the one source schema every life schema and the person schema share as `$defs.source`; a life record body names its sources under `_sources` (`SOURCES_KEY`). |
| `src/founder-puzzle.ts`, `src/files-person.ts` | The person's attributes (`ATTRIBUTE_KINDS` in `src/person.ts`: telos, ambition, passion, value, strength, weakness, puzzle, unfair-advantage, constraint, each with where Aristotle treats it; `stateAttribute`, `proposeAttributes`, `confirmAttribute`, `closeAttribute`, `currentAttributes`). `attributesFromPuzzle` reads a founder's puzzle report (`naive.founder-puzzle-source` v1) as imports, all proposed. `readPersonFile` and `writePersonFile` read and write the person record in a vault's `person.json`, keeping its id and name and checking the person schema; each write is logged in `memory.jsonl`. `person-attributes.test.ts` tests them, with Torian's two real reports where the project files are mounted. |
| `src/person-schema.ts`, `schemas/person.schema.json` | The person record's JSON Schema, from `PersonState`, with each key list typed against person.ts so a new key there fails the type check. `x-reflect` carries noun person, category substance, an external good and the person's community, from the ontology. `pnpm schemas` in `web/` writes it and `--check` fails when it is stale. `personProblems` checks a record with `src/schema-check.ts` and adds that a fact's status agrees with its source; `personFileProblems` is what `reflect check` runs on a vault's `person.json`, which normally holds only the id and name, so it checks facts, relationships and holds only when the file holds them. |
| `src/journal.ts`, `src/packs.ts`, `src/reflect.ts` | Entries and prompts, prompt packs, and reflecting with frames. |
| `src/store.ts` | The store interface, `Journal`: one person's journal, append-only, whichever host keeps it. |
| `src/layout.ts` | Where records sit in an instance folder: a vault (the lifetime folders, `journal/`, `reflections/`, `concepts/`, `documents/`, `telos/`, `intents/` at the root; `work/` ventures left to Naive) or the older `people/<id>/` layout. |
| `src/lifetime.ts` | The Ventures of a Lifetime as folders: each folder and its guide, the legacy templates, the eight needs and how each is met (`keepNeed`), the regions and their states with dated passages and the state rebuilt from them (`keepPassage`, `lifeState`), the legacy prompts, and their checks. Folders are regions and associations, never states. `readLifeRecords` reads what a vault holds for the lifecycle: passages, needs, and a record per note in `belonging/friends`, `groups` and `standing` (its front matter as the body, its `state:` line as the state). |
| `src/lifecycle.ts` | The life stages as the framework's lifecycle, the way Naive has venture phases (docs/design/REFLECT_FRAMEWORK_2026-11-19.md, step 5). `LIFECYCLE` is every state of the Ventures of a Lifetime statechart, region by region in the statechart's order, each with the life apps and record kinds it brings forward and its gates. A soft gate is a suggestion computed from the person's records and shown as evidence, never declared met; a hard gate is allowed only where another person's consent is needed (a group admits a member; a joint vault opens only when both partners join), per the domain design's "Life stages" (decided 2026-11-12). `checkLifecycle` refuses a definition that drops or reorders a statechart state, names an app or kind that does not exist, or has a hard gate that does not name whose consent it waits on. `needNow(stageState, records)`, after Naive's need-now (EE-028), says what to attend to now: every need in every stage, the kinds the current stages bring forward that are not kept yet or that a record flags (income against the intended household, a credential needed, a friend due a visit by their own "every", a relative in care with no visit in 30 days, a plan not reviewed since the latest passage, an election or duty within 30 days, a date with nothing learned written), and the next stage in each region with what the records show for its gates. Each item says the records it is read from. `needsFromLife` reads needs from the web app's Home records. Background, cited only: Rhetoric II.12-14 on the ages of life, and Physics III.1 (201a10-11) on change as the actuality of the potential. Pure: no I/O. Not built: the domain design's proposed eight stages (in others' care through death), which the statechart does not have; a gate that reads a joint vault's consent; the web app showing need-now. |
| `src/terms/ontology.json`, `src/terms/ontology.ts` | Reflect's ontology in Naive's format (Torian, 2026-11-19: own copy, Naive's format; design `docs/design/REFLECT_FRAMEWORK_2026-11-19.md`). The top categories are Aristotle's ten Categories, each mapped to a BFO class; 44 nouns name what life records are about, each with its standard, `app` and the life kinds about it (`app:kind`). `checkOntology(ontology, kinds)` returns every problem by rule: U1 cycle, U3 orphan, U4 two categories, B1 BFO class against IRI, K1 a kind listed by no noun or two, K2 a listed kind that does not exist, G1 a `good` that is not body, external or soul (`GOODS`, *Nicomachean Ethics* I.8, 1098b12), C1 a `community` that is not person, union, household, village or polis (`COMMUNITIES`, *Politics* I.2), S1 a noun named like a record listed under `sources`, S2 a `sources` BFO class other than generically dependent continuant, and a top category that is not one of the ten. `nounOfKind`, `categoryOfKind`, `goodOfKind` and `communityOfKind` read it. Goods follow the apps' grouping (Body and Home are goods of the body, the rest external), except that virtue, craft, interest, preference and end are goods of the soul, and Home's money and property (budget, belongings, purchases, life changes) are external, since Aristotle counts wealth as an external good. Information records (journal entries, reflections, conversations, imports) are listed under `sources`: sources of field values (`src/value-source.ts`), outside the ten Categories, filed in BFO as a generically dependent continuant and in IAO as an information content entity (Torian, 2026-11-20). Not built: the term engine (Naive checks term properties label-blind). |
| `src/terms/ontology-lean.ts` | Writes the ontology as Lean, `lean/Reflect/Generated/Ontology.lean` (design step 3): the ten Categories and the kept nouns as inductive types, each noun's broader links, and a certificate (rank and category, from `checkOntology`) that the Lean build checks by `decide`. `lean/Reflect/Categories.lean` proves from it that the broader relation has no cycle and each noun reaches exactly one category; see `lean/README.md`. `node scripts/ontology-lean.ts` writes the file and `--check` exits 1 when it is stale; `ontology-lean.test.ts` fails on a stale file. It refuses an ontology that fails its structural rules and two nouns with one Lean name. |
| `src/life-body.ts` | Typed bodies for the life records declared in `src/life.ts` (`DeclaredKind` keeps each kind's field keys, field kinds and inline choice ids as literal types). `kindSchema` and `bodySchema` derive a zod schema for a kind from its fields, matching what `cleanBody` keeps: text and long are strings within its lengths, number and money are numbers (unsigned ones at least 0, signed ones within 180), day is YYYY-MM-DD, choice is one of the field's option ids, check is a boolean, origins is a comma list of origin ids; every field is optional and keys the kind does not declare are kept, typed unknown. `parseBody(kindId, body)` returns the typed body (`BodyOf<K>`) or every problem, each naming the field and what was expected, never the value; it never throws. `bodyOf(kindId, body)` gives the typed body with mismatched fields left out, for code that reads fields. It is the core's one package import (zod), which the web app resolves for it through `web/tsconfig.json` paths and `web/vitest.config.ts`. The CLI never imports it, since plain Node cannot resolve zod from here: `src/life-check.ts` validates against the JSON Schemas instead. |
| `src/life-schemas.ts`, `schemas/life/` | A JSON Schema (draft 2020-12) for every life record kind, derived from its fields the way `src/life-body.ts` derives zod (`fieldJsonSchema`, `lifeSchema`, `lifeSchemaFiles`). Each carries, under `x-reflect`, the kind's app and id, its noun, its Aristotelian category, its kind of good and its community, from `src/terms/ontology.json`; a kind the ontology does not place throws. The files are `schemas/life/<app>.<kind>.schema.json`, written by `pnpm schemas` in `web/` (`web/scripts/life-schemas.ts`); `pnpm schemas --check` fails when one is missing, stale or left over, and `src/life-schemas.test.ts` checks the same and that a sample body for every kind validates against both its JSON Schema and its zod schema. Every schema also declares `_sources`, a declared field key to its source, with the shared source schema as `$defs.source` (`src/value-source.ts`); `fieldSchemaOf` gives a field's own schema. A test checks that every choice field emits `enum`. `lifeKindRefs` lists every kind as `<app>.<kind>`, and `lifeSchemaOf(ref)` finds one kind's schema by `app.kind`, `app:kind` or the kind's id alone. Two things read them: `reflect check`, through `src/life-check.ts`, and the `life_schema` action in `src/vault-actions.ts`. |
| `src/life-check.ts` | Checks a vault's life records against their kinds' JSON Schemas, for `reflect check` (`checkInstance` in `src/instance.ts` adds its problems and returns what it read as `life`). A vault keeps life records of three kinds, one note each (`LIFE_NOTE_KINDS` in `src/lifetime.ts`): friends, groups and offices in `belonging/`; a note's front matter is its body, read as a number or a boolean where the field's schema says so, with `_sources` as one line of JSON (`bodyFromFrontMatter`). `sourcesProblems` checks `_sources` against the shared source schema and names the field, never the quote. `schemaProblems(schema, body)` validates the subset of JSON Schema the life schemas use (type, minimum, maximum, exclusiveMaximum, maxLength, pattern, format date and enum) with no package, so the CLI runs under plain Node; `life-check.test.ts` checks that it refuses a wrong value of every field of every kind exactly where `parseBody` does. `checkLifeRecords` returns each kind with its folder, schema id and record count, and every problem with the record's path, app, kind and field, never the value. `lifeProblemLine` and `lifeCheckLine` are what the CLI prints. An instance in the older people layout keeps none. |
| `src/files-journal.ts` | The folder host: entries as `journal/<date>-<id>.md` (front matter optional, so a hand-written file is an entry; front matter the person adds is kept on later writes), reflections as `reflections/<entry>.json` (labelings an older version wrote are kept as they are and never read), sparks with their concept notes in `concepts/`. |
| `src/learning.ts` | What the person knows, in `learn/`, with books at the center: books (`learn/books/`, status and dates, the subjects they cover), subjects (`learn/subjects/`, nodes of the graph with `requires`, `part_of` and `same_as`, aspire or need, and dated grasp lines the person gives: teach, explain, gist or forgot), resources (`learn/resources/`, other links, including posts and threads whose `source` (x, substack, reddit, youtube) is read from the link), films (`learn/films/`), talks (`learn/talks/`, someone the person saw speak) and conversations (`learn/conversations/`). Subjects are inputs, fields the person studies; `shown by` lines (someone saw the person display knowledge) and `suggested by` lines are never grasps. A book or film can be `referenced` (cited, how far read not said). `learnMap` derives known from the latest grasp, shown and suggested apart from it, the subjects of a read book not yet rated, and the fringe. Nothing is known until the person rates it. `learnProblems` checks it. |
| `src/ideas.ts` | The person's own ideas, outputs kept apart from learn (`ideas/`): each restatement is a dated `stated` line, inputs are `from` (the person says it fed the idea) or `maybe from` (they suspect so), and recommendations are a separate list placed `supports`, `extends`, `parallels`, `challenges` or `opposes`, with who suggested them. A target is a vault note or the person's words with an optional link. Lines are never rewritten; `foldIdea` lets the latest line about a thing decide where it stands, and the web app folds its rows with the same code. `ideaProblems` checks it. `ideasNaming` lists the ideas that name one thing (a book by its ref), each with how: came from it, may have, or its place on the spectrum. |
| `src/naive-handoff.ts` | Sending an idea to Naive on the person's say-so. Reflect never imports Naive: `sendIdea` runs the person's own `naive capture` (or `NAIVE_BIN`) in their Naive workspace (`findNaiveWorkspace` looks above the vault for `naive-workspace.json`), with `handoffText`: the title, the latest statement, the `from` inputs and a line naming the idea note. Maybe-inputs and recommendations stay in Reflect. The idea then gets a dated `sent to naive <workspace>:raw/<file>.md` line (`SENT_LINE`, read by `sentOf`). |
| `src/catalog.ts` | `index.md`, the vault's catalog, where the person's own AI starts reading. `buildIndex` lists every note by folder with one wikilinked line (ideas with their statement and inputs, subjects by grasp or want, books, films, talks, conversations, links, concepts, ventures under `work/`, sources) and the folder guides; journal entries are listed by date only, never their text. `writeIndex` rewrites it and reports whether anything changed. It is derived from the notes and holds no fact of its own. |
| `src/wiki.ts` | The wiki: a compiled view of the vault written by the person's own AI, kept apart from the record (after Farza's personal wiki skill). `wikiOn` turns it on (off by default). `wikiPrompt` gives the AI the writer's instructions, `index.md`, the wiki so far and up to 15 journal entries not yet absorbed (pointer entries read live). `readWikiReply` checks each article (`checkArticle`): a `<folder>/<slug>` path, no em dash, every paragraph, list item and table row citing a note in the record (a "See also" line of wiki links is exempt), and every quote of four words or more found in what its passage cites; refused articles are listed with why, and the rest wait as a draft in `.reflect/`. `keepWikiDraft` writes the chosen articles (front matter with type, aliases, related, cited sources), logs absorbed entries in `wiki/_absorb.json` and rebuilds `wiki/_index.md` and `wiki/_backlinks.json`. A pattern, tension, identity, philosophy, life theme, assessment or metaphor is `reading: ai` until `confirmReading`; the confirmation holds for that text's hash, so a rewrite makes it a reading again. `wikiProblems` names an article citing a note that left the vault. |
| `src/sources.ts` | The person's other folders, pointed at instead of moved in. `addSource` names a folder outside the vault in `sources.json`; `indexSource` fingerprints its files into `.reflect/index/` (derived, git-ignored), leaving out hidden folders, dependencies, exclusions and names that look like secrets. `placementPrompt` asks the person's own AI where each open file belongs (book, film, talk, link, conversation, subject, idea, entry, venture, document or none); `readPlacements` reads its reply, keeping only files in the index; `keepPlacements` turns each chosen one into a dated `pointer <source>:<path> #<sha>` line on its note and a line in `sources/<name>.md`. An entry (a plain text file) becomes a closed journal entry whose front matter is `pointer: <source>:<path>` and `pointer_sha`; `filesJournal` reads its text from the file each time (`pointerText`), so it is listed and reflected on without a copy, and placing it again keeps the same entry. A venture maps to its Naive folder `work/<slug>` when there is one (Reflect never writes inside it); without one, a venture with a statement is kept as an idea with the pointer, and one with neither is only mapped, with a note saying so. A document becomes a custody card whose `where` is the file. Nothing in a source is moved, edited or copied. `sourceStatus` and `sourceProblems` report placed files that changed or vanished. |
| `src/sweep.ts` | The memory sweep: `SWEEP_PROMPT` for the person's own AI, `readSweep` for its JSON reply (`reflect.learn-source` v1), and `keepSweep` for the items the person chose. Inputs and ideas are kept apart; an idea's input the AI only inferred is kept as maybe from; nothing sets a grasp. |
| `src/openlibrary.ts` | Looking a book up in Open Library: `searchBooks` by title or author, `browseClass` for one Library of Congress main class (best rated first, paged), `lookupIsbn` for one edition with its work's subjects and table of contents, all over an injected fetch. `cleanEntry` cuts an entry that came back from a browser to the fields and sizes Reflect keeps. The catalog is editable by anyone, so its entry is a suggestion saved beside the book note (`learn/books/<book>.openlibrary.json`); the book note changes only by the person. Each entry also keeps the work's Library of Congress call numbers (`lcc`), which put the book on its shelf, and its cover id (`cover`, drawn by `coverUrl`). `trendingBooks` is what is read on Open Library this week; `workEntry` looks one work up by id to fill in call numbers. `browseQuery` runs any search query (as `themaQuery` writes them), best rated or most logged first; entries in lists carry readers' ratings (`rating`). `workDetails` reads what a book page shows: the work's description, its rating and its editions (English first). Lists are in one language, `LANGUAGE` (English for now): searches keep works with an English edition (`language:eng`) and show that edition's title and cover, this week's reads keep the ones with an English edition, and an ISBN search finds any language. Authors: entries keep their authors' ids (`authorKeys`); `authorDetails` reads one author (life dates, biography, photo for `authorPhotoUrl`, Wikipedia link), `authorWorks` lists their books, and `searchAuthors` finds authors by name, leaving out one-work duplicates. Lists can be in four orders, `SORTS`: best rated, most read, newest, oldest. `workAccess` reads where a work is free from the catalog's own links (the Internet Archive's scan, public or to borrow; Project Gutenberg, Standard Ebooks and LibriVox ids); `booksLike` lists the most read books on a work's first subject that is not too broad (`BROAD_SUBJECT`); `workDetails` also keeps editions' covers and page counts and the first English table of contents. |
| `src/claims.ts` | Claims in Learn: something a person holds true or false, with holders named and cited. The stance is one of the three doxastic attitudes (belief, disbelief, suspension of judgment); stances are dated lines, never changed, and `currentStance` takes the latest. `cleanClaim` checks a claim and its holders. |
| `src/thema.ts` | Learn's categories: Thema, the book trade's subject scheme (EDItEUR v1.7, free to use), its 20 sections as parents and two-letter categories as children, with Thema's own headings. Open Library does not carry Thema, so `categoryOf` places a book: fiction and children's books by their catalog subjects (genre), then its call numbers through Reflect's own crosswalk to Library of Congress ranges (narrowest range wins), then subjects; when nothing places it, nothing is guessed. `themaQuery` writes the Open Library search for a section or category (call-number ranges where it has them, subjects otherwise, fiction without children's books). `shelveThema` puts books in sections and subjects where most of their books are. `showCall` prints a call number as a library does. |
| `src/gutenberg.ts` | Project Gutenberg's plain texts (no key) for the reader inside Reflect: `gutenbergBook` fetches one by id, `chaptersOf` cuts the header and licence, joins hard-wrapped lines into paragraphs and splits the text into chapters (headings in title case; a text with none is cut into parts). | `src/standardebooks.ts` | Standard Ebooks' proofread, typeset public-domain books (no key): `standardBook` reads one book's single-page edition, and `standardChapters` cuts its body matter into chapters of plain paragraphs, taking note marks out of the text and keeping where they sat; `standardNotes` reads the endnotes. Nothing is saved. |
| `src/reading.ts` | Reading arithmetic: words and minutes per chapter (238 words a minute), time left in the chapter and the book, `searchBook` and `findSpans` for a phrase in the text, and `carryPlace` to carry a kept place to a text with another chapter count. |
| `src/wiktionary.ts` | A word looked up while reading: `definitionsOf` reads the English senses from Wiktionary wikitext with their usage labels, marking older meanings (archaic, obsolete, dated); `lookupWord` takes one word from a selection. |
| `src/home-cards.ts` | Home cards (Ask Reflect, 2026-11-17): small cards a model places on Home for a time, like a vocabulary widget. | `src/free.ts` | Whether a book can be read or heard in Reflect: `freeIndex` indexes a catalog of free books (lines of id, title and author) by title word, and `findFree` finds a book in it by every word of its title and a name of its author; `freeEditions` and `editionsOfId` find every text of the same book, each translation with its translators. `openlibrary.ts` marks each entry with `free` once the app calls `knowFree`. |

| `src/book.ts` | The book of your life: `DOMAINS` (the chapters, the Ventures of a Lifetime domains in chart order), `BELIEF_KINDS` and `checkKind` (after Aristotle, an ideal is what is best as one would pray for it, wished for as an end; a practical belief is what is best for me now, which must name the ideal it serves and the circumstances it is for), `bookEntry` (held now, or once held and no longer, with dates, kind, origins and what it serves), `compileBook` (every chapter kept; held beliefs before revisions; ideals, then practical beliefs, then unmarked; unplaced beliefs apart) and `bookMarkdown` (a dated edition grouped the same way, with citations, origins, sources and struck-through revisions). |
| `src/origins.ts` | Origins: Aristotle's seven causes of action (*Rhetoric* I.10) in his grouping, three not from the person (chance, nature, compulsion) and four from the person (habit, reasoning, spirit, appetite; origins kept as anger read as spirit); `cleanOrigins` keeps known ones once each, in his order. |
| `src/goodreads.ts` | Reading a Goodreads library export (CSV): `csvRows` (RFC 4180, quoted commas, doubled quotes, newlines) and `readGoodreads` (each row a book: title, authors, ISBN, Exclusive Shelf as want, reading or read, Date Read as the finish day). No network. |
| `src/chat.ts` | `chatJson`: one JSON reply from gpt-oss, through Vercel AI Gateway (the web app adds the OIDC token) or Ollama. Used to read a transcript and by the CLI. |
| `src/bundle.ts` | A bundle: one person's journal as one JSON document, the same from either host. Moving hosts is an export from one and an import into the other's empty journal. |
| `src/theme.ts` | The app's themes. |
| `src/audience.ts` | Who sees a record on the shared side (doc "Private and shared Reflect plan", step 3): `RECORD_AUDIENCES` (only me, people I invite, people I've met, everyone, widening in that order), `canSee(audience, viewerRelation)` for a viewer who is the owner, invited, met, signed in or anyone, and `audienceOf(kind, own)`, which gives a record with none its kind's default (an adventure: its owner and the people on it; every other kind: only the owner). The profile's three audiences (`src/profile.ts`) are among them. Kept on `life_record.audience` (web migration 0063). |

Modules import each other by their `.ts` names and import JSON with `with { type: "json" }`, so Node runs them directly (`node -e 'import("./src/journal.ts")'`, Node 22.18 or later).

## The action registry: what is not built

The framework and the journal's four actions are here. The app's other declarations (about 200, in `web/src/server/actions/`) are not moved yet: their inputs are zod schemas and their runs call the app's Postgres stores, and most of those stores have no files host here. Each moves when its store gets a files host, the way the journal's did. A vault offers no shared, outside or publishing action yet, so nothing is held over its MCP server, and nothing in the CLI approves or declines a held change. The presentation gate's actions are the vault's alone: the app keeps no presentation records, and the tcjcafe.com GitHub save does not go through the gate yet.

## Tests

`pnpm test` in `web/` runs `src/*.test.ts` with vitest. The app still calls the Postgres store's functions directly.
